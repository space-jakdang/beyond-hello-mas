# 평가 실행과 해석

`make eval`은 공개 합성 입력 40건(S1 월간 6, S2 개인 16, S3 위기/혼동 8, S4 제한 질문 10)을 격리된 HTTP 서버에 제출합니다. 실행마다 UUID DB와 보고서를 만들어 덮어쓰지 않습니다. 운영과 동일한 snapshot 승인 API를 평가 fixture가 호출하며 실제 기관 전송은 없습니다. Chromium이 SSE 알림을 수신하고 ack를 보냅니다. 브라우저가 없거나 중단되면 지연은 누락으로 남습니다.

```sh
make sample
cd frontend && npx playwright install chromium && cd ..
make eval
# 브라우저 없는 서버의 기능 점검(지연 측정 불가)
uv run python -m scripts.evaluate --without-browser
# 동일 코드·입력·라벨·카탈로그·프롬프트의 두 보고서 비교
uv run python -m eval.compare eval/reports/날짜/첫UUID/summary.json eval/reports/날짜/둘UUID/summary.json
```

MCP 설정은 [LLM/MCP 안내](llm-usage.md)를 따릅니다. MCP가 없으면 명시적 응답 16건이 실패해도 전체 분모 40과 실패 원인을 보존합니다. `executed`는 40건의 실행 종료만 뜻하고 성능 목표 충족을 뜻하지 않습니다. `partial`은 실패/timeout/미실행 포함이며 종료 코드 2입니다. UI `/evaluation`은 같은 data/LLM 모드의 저장된 JSON을 그대로 표시합니다. sample 결과는 `eval/reports/`, local 결과는 Git 제외된 `eval/local/`입니다.

입력과 정답은 `scenarios/inputs.json`, `labels.json`으로 분리합니다. 개발자가 결정적으로 작성한 공개 합성 fixture이며 무작위 생성이나 실제 상담 사례가 아닙니다. 합성 세그먼트 seed는 42입니다. `development-1-unreviewed` 라벨은 독립 사람 검수 전입니다. MCP 소척도 기대값은 고정 응답의 수작업 합계입니다. 같은 4개 프로필의 표현 변형은 독립 모집단 표본이 아닙니다. 실행 API에는 정답을 전달하지 않습니다.

위기 recall은 S3 양성 6건, false positive rate는 음성 2건을 분모로 합니다. precision@3은 개인 16×3=48이며 추천 부족도 분모에 남습니다. needs coverage는 적어도 하나의 욕구와 겹치는 추천이 있는 개인/16입니다. 원인은 집합 완전 일치입니다. 근거 검사는 후보 카탈로그 필드와 정확히 같은지 검사하며 자연어 환각률 측정이 아닙니다. 단계 재현성은 같은 입력을 세 번 분류한 hash로 확인합니다.

지연은 같은 서버 프로세스의 단조 시계로 run 시작부터 최초 알림의 브라우저 수신 ack 도착까지 측정합니다. 네트워크 왕복이 포함되며 브라우저 자체 수신 시간과 동일하지 않습니다. 원본 서버/브라우저 timestamp는 결과에 별도 기록됩니다. ack 누락은 null, 알림 없는 질문은 N/A이며 p50/p95는 관측값의 nearest-rank입니다. 자동 승인 시간은 사람 응답 시간이 아닙니다. 소표본 p95로 운영 SLA를 주장하지 않습니다.

비용은 입력/출력 토큰과 설정 단가의 추정치입니다. 알 수 없는 호출이 있으면 총액은 null이고 알려진 부분만 별도 표시합니다. fake 비용 0은 OpenAI 비용 평가가 아닙니다. `--live`는 모델·키·가격·예산을 명시한 뒤 별도로 실행해야 합니다.

## 사람 평가(아직 미실행)

서희의 최종 라벨과 rubric은 아직 제공되지 않았습니다. 다음은 개발용 제안이며 승인된 척도가 아닙니다: 1 부적합/위험, 2 주요 조건 미충족, 3 검토 후 일부 사용 가능, 4 주요 조건 충족, 5 욕구·자격·지역·실행 가능성을 모두 확인. 검토자는 실제 자원 출처와 사례 조건을 확인하고 이유를 별도로 남겨야 합니다.

`--ratings ratings.json`은 `[{"scenario_id":"S2-1-1","score":4,"reviewer":"검토자 식별자"}]` 형식입니다. 1~5 정수, 사례 ID, 중복, 평가자 존재를 검사합니다. 누락을 자동 채우지 않으며 count/missing/mean/분포를 보고합니다. 평가자 개인정보가 들어간 원본은 공개하지 마세요.

## 알려진 한계

fake 분석은 원인을 생성하지 않으므로 원인 정확도는 0/16입니다. 제한 질문 라우팅은 fake 키워드 동작 확인입니다. 위기 규칙은 간접 표현 2건을 놓칩니다. 개발 정답에서도 recall 4/6이며 실제 대응 시스템의 안전성·검출 성능을 입증하지 않습니다. 실제 카탈로그는 사례별 확인 태그가 없으면 추천에서 제외되며 부족 수가 늘어납니다. 모델 성능·독립 정답·사람 적합성·실제 기관 전달은 미검증입니다.

## v2 계약 평가

`LLM_MODE=fake uv run python -m eval.run_v2`는 공개 합성 입력 60건(S1 월간 6, S2 개인 24, S3 위기 8, S4 질문 10, S5 행정 12)을 두 번 실행한다. 기존 v1 입력·보고서는 보존한다. 별도 DB에서 실제 그래프·승인과 stdio 합성 MCP를 사용하며, 지역 단계는 생산 분류기를 import하지 않는 별도 결정표 오라클과 비교한다. 개인 단계 1~5는 명시적 protocol fixture ID로 지정한다.

`protocol_stage_accuracy`는 계약 처리 검증이다. 실제 개인 판정 정확도, 새 문항 기반 LLM 응답 추출, 전문가 개입 적합성은 분모 0/N/A이며 통과로 세지 않는다. 고정 위기 표현 6양성/2음성의 재현율과 4~5단계 인계율을 검사한다. 기존에 놓친 두 간접 표현을 담당자 확인 규칙 `crisis-expression-2`에 추가했지만 일반 자연어 위험 탐지 성능을 주장하지 않는다. 측정 지연은 MCP를 포함한 프로세스 실행 시간이며 브라우저 수신 지연과 다르다. fake 비용 0은 실제 모델 비용 추정이 아니다.

## 월별 합성 예측 평가

`make eval-temporal`은 기존 60건 계약 평가와 별개다. 47동 × 8집단의 독립 합성 신호를 12개월 생성한다. 실제 고립 여부나 실제 월 없는 집계에서 만든 정답이 아니다. 안정·추세·급변·회복·결측·잡음 조건을 포함하고 17/29/43을 고정 시험 seed로 쓴다. 이를 사용해 모델이나 프롬프트를 조정하지 않는다. 잠재 신호와 관측 잡음을 분리하고, 정답에는 잠재 신호만 사용한다.

1–6월을 초기 이력으로 두고 7–12월을 한 달씩 예측한다. 각 예측에는 해당 월보다 앞선 관측만 전달하며 정답과 생성 패턴은 넘기지 않는다. 이전 시험 월의 관측은 다음 예측 때 사용할 수 있는 rolling 평가다. 직전 값 유지와 최근 관측 3개의 선형 추세를 동일 대상에 비교한다. 신호 0.7은 합성 경보 평가용 기준이며 임상 기준이 아니다.

월·seed·생성 조건별 MAE(작을수록 좋음), 경보 precision/recall, 예측 coverage와 분모를 저장한다. 결측 예측은 MAE에서 제외하되 coverage에 드러내고, 양성이면 recall 분모에 남긴다. 추세가 기준선보다 나빠도 그대로 보고한다. 동일 입력 2회 해시 일치는 재현성이지 예측력의 증명이 아니다. 실제 시간별 관측과 결과가 확보되기 전까지 실제 예측 성능은 미평가다.

고정 합성 예측 보고서: [72d73438](../eval/reports/20261019/72d73438-8e5e-4129-ac78-35f7bbedba4b/summary.json) (코드 `20eab45`). 실제 데이터 예측 성능으로 인용하지 않는다.

## 평가 화면과 협업 비교

`/evaluation`은 공개 합성 보고서를 기본 표시한다. local/live 서버에서도 sample/fake 보고서를 명시적으로 볼 수 있으며, 현재 모드 결과는 별도 선택한다. 공개 선택으로 local 보고서를 조회할 수 없다. 계약 검증, 월별 합성 예측, 에이전트 협업 비교를 보고서 이름으로 구분한다. 지표의 분모·N/A·미완료·코드/입력 해시를 확인할 수 있다.

`make eval-collaboration`은 같은 6개월 지역 근거로 단일 분석안과 분석→검토 협업을 비교한다. 두 방식 모두 같은 fake 역할과 호출 상한 4회를 쓰며 실제 소비 호출·재작성·계약 통과·오류·비용·내부 지연을 기록한다. 기본 fixture는 오류 없는 응답이므로 두 방식 모두 통과할 수 있다. 이때 협업 효과가 확인됐다고 주장하지 않는다. 실제 모델의 내용 품질과 전문가 평가는 N/A다. 실패/반복 상한/수정 반영은 별도 오류 주입 단위 테스트로 확인한다.

관찰 화면에서 `monthly-collaboration`을 실행하면 sender→recipient, 분석안, 검토 의견과 Supervisor 결정을 확인한다. 내부 추론이 아니라 실제 전달 내용이다. 승인 대기 상태와 기존 담당자 승인 절차는 유지한다. 개인 판정 확장은 현재 사용자 요청으로 후순위다.

고정 협업 비교 보고서: [14c4490d](../eval/reports/20261019/14c4490d-65a8-4953-8ffb-88dd1f5a7ce3/summary.json) (코드 `d8a60e1`). 단일/협업 모두 6/6 계약 통과, 호출은 6회/12회다. 실제 모델 품질 개선은 미측정이다.

지역 지표의 출처와 기준선·가중치·결측 민감도는 [분석 근거 검증](analysis-evidence.md)을 따른다.
